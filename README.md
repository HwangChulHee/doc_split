# docsplit

여러 대출 서류가 페이지 단위로 뒤섞인 하나의 PDF를 입력받아, 각 페이지를 문서
유형(`URLA_1003` / `CREDIT_REPORT` / `TITLE_REPORT` / `INCOME_DOC` / `OTHER`)으로
분류하고, 문서 단위로 다시 묶은 뒤 문서 내 페이지 순서를 복원하는 파이프라인입니다.

## 접근 방식

전체 판정 경로는 **규칙 → LLM → UNRESOLVED** 입니다. 규칙이 확신하는 페이지는
규칙으로 확정하고, 확신하지 못하는 페이지만 LLM으로 보내고, LLM도 확신하지
못하면 UNRESOLVED로 남깁니다.

이 구조를 받치는 판단은 세 가지입니다.

1. **규칙은 데이터가 아니라 준거 문서에서 추출했습니다.** 정답이 있는 패키지가
   39페이지뿐이라 여기서 규칙을 뽑으면 표본 과적합이라 생각했고, 유형별 준거
   문서(공식 표준 양식·정부 발행물·벤더 제품 문서)를 직접 확보해 규칙을
   추출했습니다. 데이터는 대조 용도로만 썼습니다.
2. **가중치 점수는 쓰지 않았습니다.** 결정적 신호 1개면 확정, 지지적 신호
   2개면 판정, 그 미만이면 LLM 이관 — 임계값이 1과 2뿐이라 데이터에 맞춰
   조정할 여지가 없습니다.
3. **LLM은 규칙이 확신하지 못하는 곳에만 씁니다.** 미확정 페이지 분류, 텍스트
   없는 스캔 페이지의 비전 판정, 그룹핑·순서 복원의 판단에 사용하고, 모든
   판단에 근거(evidence)를 남기게 했습니다.

세부 내용은 이어지는 섹션에 있습니다 — 준거 확보 내역과 신호 계층은 아래에,
검토하고 배제한 대안은 [설계 결정과 근거](#설계-결정과-근거), 원칙이 실제
결과에 어떻게 나타났는지는 [결과](#결과)에 정리했습니다.

### 준거 확보 내역

| 유형 | 확보한 준거 | 근거 등급 |
|---|---|---|
| URLA_1003 | Fannie Mae·Freddie Mac 공식 blank 양식 (양쪽 모두) | 표준 검증 |
| CREDIT_REPORT | 벤더(Xactus) 공식 Reference Guide 3종 | 벤더 문서 검증 |
| TITLE_REPORT | 2021 ALTA Commitment blank (주 규제기관 게시본) + 벤더 가이드 | 협회 표준 / 벤더 문서 |
| INCOME_DOC | IRS transcript 공식 샘플·안내, IRS 양식 blank 5종 | 정부 표준 |

- 신호마다 출처 계층을 표기했습니다. 법·표준이 강제하는 신호(`normative`)와
  업계 구조상 필연인 신호(`domain`)만 분류 규칙으로 채택했고, 벤더 고유
  신호(`vendor`)는 분리 레이어로 관리하며, 조판·인쇄 산물(`deployment` —
  페이지 번호 등)은 분류에서 빼고 그룹핑 재료로만 썼습니다.
- 준거 대조에서 얻은 것도 있습니다. URLA 페이지 번호(`3 of 11`)는 공식 blank에
  없는 렌더링 산물임을 확인해 분류에서 뺐습니다. 판별 기록은 `docs/analysis/`에
  있습니다.

### LLM 사용 지점

- **분류**: 규칙이 확정하지 못한 페이지만 gpt-5.4-mini로 페이지당 1회 호출합니다.
  5개 유형 후보와 규칙이 찾은 신호를 함께 넣습니다.
- **스캔 페이지**: 텍스트가 없는 페이지는 렌더링 이미지를 같은 모델의 비전
  입력으로 판정합니다.
- **그룹핑·순서 복원**: 코드가 신호(이름·ID·페이지 마커)를 수집하고 LLM이
  문서 단위로 묶습니다.

## 파이프라인 구조

실행 시 진행 상황이 `[1/8]` ~ `[8/8]`로 출력됨. 8단계는 아래와 같음.

```text
data/*.pdf
   │
   ▼
[1] 입력 인식            파일명으로 분류 대상 / 정답 원본 구분 (인식 결과를 표로 출력)
   ▼
[2] 텍스트 추출          PyMuPDF — 페이지 원문 + 메타데이터
   ▼
[3] 규칙 분류            4개 정책(policies/*.yaml)을 페이지마다 동시 평가
   │                     RULE_HIGH > RULE_MEDIUM 우선순위로 확정
   ├─ 미확정 ──► [4] LLM 분류    5유형 후보 + 규칙 평가 결과 동봉, 페이지당 1회
   ├─ 텍스트 없음 ► [5] VLM       dpi 150 정방향 렌더링 → 비전 분류
   ▼
[6] 그룹핑 (LLM)         코드가 신호 카드(이름·ID·마커·코드)를 모으고
   │                     LLM이 유형별 문서 instance로 묶기 — evidence 필수,
   │                     근거 없는 페이지는 미배정으로 남김
   ▼
[7] 순서 복원 (코드)      마커가 온전하면 마커 정렬, 아니면 표준 구조 순서로 대체 정렬
   ▼
[8] 결과 저장            results/ — 분류 CSV · 문서 구성 JSON · 요약 · 검증 리포트
```

- 정책과 프롬프트는 코드에서 분리 (`src/docsplit/policies/`, `src/docsplit/prompts/`)
  - 규칙의 정의 → yaml, LLM 지시 내용 → md
- 유형·벤더 추가는 파일 추가만으로 가능 — 엔진 코드 무수정 구조

## 결과

### package_01 (정답 대조)

| 항목 | 결과 |
|---|---|
| 페이지 분류 | **38/39 (97.4%)**, macro F1 0.985 |
| 그룹핑 | 3개 instance (URLA 11장 · CREDIT 18장 · TITLE 8장). INCOME 1장은 어느 instance에도 미배정 |
| 순서 복원 | URLA 11장·TITLE 8장 **완전 복원**(페이지 마커 경로). CREDIT은 마커가 없어 구조 순서로 14장 대체 정렬 + 4장 미해결 — 배열한 순서도 원본과 불일치 |

- 유일한 분류 불일치는 오분류가 아니라 의도된 미확정
- plat map이 제거된 자리 페이지 → 텍스트 근거가 물리적으로 부재 → UNRESOLVED
- 근거 없는 페이지를 추측으로 배정하지 않는다는 원칙의 결과. 이 1페이지를 잡기 위한 규칙-데이터 끼워맞춤은 배제

### package_02 (정답 없음 — 최종 분류 결과)

| 유형 | 페이지 수 |
|---|---|
| CREDIT_REPORT | 15 |
| TITLE_REPORT | 14 (스캔 3장의 VLM 판정 포함) |
| URLA_1003 | 10 |
| INCOME_DOC | 4 |
| UNRESOLVED | 1 (유형 신호가 고지문 한 줄뿐인 transcript 연속장) |

- 판정 경로: 규칙 37장(84%) / LLM 3장 / VLM 3장 / 미확정 1장
- 문서 구성: 총 5개 instance — URLA 10장, CREDIT 15장, INCOME 3장, TITLE 2개(10장·3장)
- TITLE 10장짜리는 거의 동일한 Commitment **두 벌**이 한 instance에 뭉친 상태
  - 페이지 마커 중복(`Page 1 of 5` 두 장)으로 두 벌임은 감지
  - 어느 장이 어느 벌인지 가를 근거가 신호 카드에 부재 → 분리 실패 (아래 한계 4번)
- 3장짜리는 마커 분모가 4로 다른 별도 출력본 — 두 instance를 `related_to`로 연결하고 차이점을 근거로 기록
- 귀속 미정 페이지 2장 (TITLE 1 · INCOME 1) — 붙일 instance의 근거가 신호 카드에 없어 미배정. 상세 사유: `results/package_02/summary.md`

## 설계 결정과 근거

주요 결정과 검토한 대안은 `docs/`에 유형별로 기록.

- `docs/domain_knowledge.md` — 모기지 서류 도메인 정리 (유형별 기능·발행 주체·표준화 수준)
- `docs/classification/*.md` — 유형별 신호 정의·근거 등급·알려진 한계
- `docs/analysis/*.md` — 준거 문서 확보 경위와 기계 대조 결과

채택하지 않은 방법과 이유:

| 대안 | 배제 이유 |
|---|---|
| supervised ML 분류기 | 표본 39페이지, 클래스 불균형(INCOME 1장), 문서 다양성 부재 → 학습 불성립. 성립해 보여도 표본 과적합 |
| 전 페이지 LLM 분류 | 규칙만으로 84% 확정 상황에서 전량 LLM은 비용·재현성·설명력 모두 불리. 규칙이 확신하지 못하는 잔여 페이지에만 사용 |
| 임의 가중치 점수제 | 왜 그 숫자인지 답할 수 없는 값은 배제 |
| 페이지 번호 기반 분류 | 표준 blank에 페이지 번호 부재를 확인. 렌더링 산물은 분류가 아니라 그룹핑 신호로 사용 |

## 알려진 한계와 개선 방향

1. **무표준 개인 작성물(P&L 등)은 규칙으로 커버 불가.** GSE 가이드라인조차 형식 요구 없음(내용 3요소와 서명만 요구). LLM의 의미 판단이 유일한 경로이고 그 뒤에 안전망 부재
2. **발행 경로와 기능이 충돌하는 경계 문서 존재.** 신용조회 벤더가 배달한 고용 검증 페이지는 발행 경로로는 CREDIT, 기능으로는 INCOME. 라벨링 정책상 기능 기준(INCOME)이 맞다고 판단했으나 규칙·LLM 모두 CREDIT 선택. 이 한 페이지를 위한 예외 규칙은 원칙 훼손으로 보아 한계로 유지
3. **마커 없는 본문 연속 페이지는 순서 복원 불가.** 신용보고서의 tradeline 표 연속장이 해당. 벤더 문서의 섹션 나열 순서를 거시 순서로, 마커를 미시 순서로 조합하는 방식이 개선 방향
4. **동일 문서의 두 출력본을 짝 맞추는 재료 부족.** 두 벌의 신호 카드가 동일(값 차이는 보험금액 한 줄) → 벌 구분 불가. 마커 충돌 감지 시 해당 페이지 원문을 그룹핑 입력에 동봉하는 내용 기반 경로가 개선안
5. **벤더 레이어에는 데이터에 등장한 벤더만 등록.** 미등록 벤더 문서는 universal 신호(측정 결과 CREDIT 기준 83% 커버)와 LLM 경로로 처리. 신규 벤더 지원은 정책 블록 추가로 가능
6. **스캔 페이지 회전을 메타데이터로 판단하지 않고 무조건 무시.**
   - 약관 스캔 3장은 `/Rotate` 값이 실제 스캔 방향과 불일치 — 렌더러가 그 값을 적용해 뒤집히거나 누운 이미지가 모델에 전달되던 상태
   - 저장된 회전값을 무시하고 콘텐츠 스트림 그대로 렌더하도록 변경(dpi 150 상향), 세 장 모두 정방향임을 육안 확인
   - 단, 이는 "`/Rotate`는 항상 틀렸다"는 가정 — 회전값이 내용과 맞는 PDF에서는 반대로 어긋남. 렌더 결과에서 글자 방향을 판별해 회전을 정하는 것이 제대로 된 해법

## 실행 방법

```bash
git clone https://github.com/HwangChulHee/doc_split.git && cd doc_split
```

1. **데이터 배치**: 전달받은 PDF를 `data/`에 원본 파일명 그대로 넣습니다. (하위 디렉토리를 포함해 넣어도 재귀 탐색 가능)
2. **API 키 설정**:
```bash
cp .env.example .env      # OPENAI_API_KEY 입력
```

### Docker (권장)

Python이나 uv를 설치하지 않아도 되므로 Docker 실행을 권장합니다.

```bash
docker compose run --rm docsplit
```

`results/`와 `outputs/`는 호스트 디렉토리에 그대로 생성됩니다. 이미지에는 코드·정책·프롬프트만 포함되고, 문서 PDF는 실행 시점에 읽기 전용으로 마운트됩니다.

API 키 없이 규칙 판정까지만 실행:
```bash
docker compose run --rm docsplit docsplit run --no-llm
```

### uv (로컬 Python 3.12 · uv 환경)

```bash
uv run docsplit run
uv run docsplit run --no-llm      # API 키 없이 규칙 판정까지만
uv run pytest                     # 판정·정렬 로직 테스트 (36건)
```

### 산출물

| 산출 경로 | 내용 |
|---|---|
| `results/package_<label>/` | 최종 결과 — 분류 CSV, 문서 구성 JSON, 요약, (정답이 있는 경우) 검증 리포트 |
| `outputs/` | 중간 산출물 — 페이지 원문, 신호 카드, LLM 캐시. 개인정보 포함되어 커밋하지 않음 |

호출 결과는 `outputs/llm_cache/`에 캐싱되어 재실행 시 API 호출 없음 — 두 실행
방식이 같은 캐시를 공유함. 비용 실측치는 [결과 > 비용](#비용) 참조.

## 프로젝트 구조

```text
src/docsplit/
├── policies/        # 유형별 신호 정책 (yaml) — 규칙의 전부
├── prompts/         # LLM 지시문 (md) — 수정 이력을 주석으로 기록
├── cli.py           # docsplit run — 8단계 오케스트레이션
├── discover.py      # data/ 입력 파일 인식 (분류 대상 / 정답 원본)
├── pdf_parser.py    # PyMuPDF 텍스트 추출 · 페이지 렌더링(VLM 입력)
├── parse.py         # 페이지 산출물 내보내기 (jsonl · 육안 검토용 텍스트)
├── stats.py         # 페이지 집계 통계 (원문은 남기지 않음)
├── normalize.py     # 텍스트 정규화 (특수문자·공백·인용부호 통일)
├── signals.py       # 정책 로드·신호 매칭
├── classify.py      # 신호 등급 결합 규칙 (결정적/지지적 → 등급)
├── unified.py       # 4개 정책 동시 평가 → 페이지 유형 확정 (실행 경로의 판정기)
├── cards.py         # 신호 카드 추출 (regex + AcroForm 폼필드)
├── grouping.py      # LLM 그룹핑 + 순서 복원
├── llm.py           # OpenAI 클라이언트 · 캐싱 · 사용량 집계
├── results.py       # results/ 산출 · 정답 대조 채점
├── ground_truth.py  # 정답 빌더 (원본 PDF를 보는 유일한 모듈)
```
